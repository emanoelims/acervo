# Phase 3 — AI Enrichment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every captured link gets one Claude call that:
- describes its first image (`image_description`, editable by the owner);
- detects the page's `language`;
- suggests 1–3 collections, either existing ones or new names with a short reason.

The inbox then becomes a triage screen: dashed ✦ suggestion chips that accept on click, "accept all", and ✓ to finish. Suggestions never auto-apply. Every call's tokens and cost are recorded. Shipped as `0.8.0` (issue #42).

**Architecture:**
- **`Acervo.AI`:** the Claude client behind a behaviour (`Acervo.AI.Client`, implemented by `Acervo.AI.Claude` with ReqLLM), the prompt and output normalization (`Acervo.AI.Enrichment`), per-call cost records (`ai_calls`), and the `Acervo.AI.EnrichLink` Oban worker on the existing `ai` queue.
- **`Acervo.Collections`:** owns `collection_suggestions`, acceptance, dismissal and repointing. It writes through the database-checked ownership from #48.
- **`Acervo.Library`:** gains the enrichment fields on `links`, the editable image description, pending suggestions preloaded on every link, and the enqueue points.

LiveView updates keep using `"links:#{user_id}"`. When enrichment finishes, the worker calls `Library.broadcast_updated/2`, and `ArchiveLive`'s existing `{:link_updated, _}` handler re-fetches the link with its suggestions.

**Tech Stack:** Phoenix 1.8 / LiveView 1.2, Ecto + Postgres 18, Oban 2.24, Req 0.7, ReqLLM `~> 1.28` (new; Anthropic provider, `generate_object` with structured output), `image` (libvips) for downscaling.

**Spec:** `docs/superpowers/specs/2026-10-18-acervo-design.md`, sections Data model (`collection_suggestions`), AI enrichment, Interface → Inbox, Configuration. **Prototype:** `docs/superpowers/specs/2026-10-18-acervo-prototype.html`: `.chip.ai`, `.ibar` and `.done`. **Reference implementation:** `../leitor`:
- `lib/leitor/language/provider.ex`: `ReqLLM.generate_object/4`, `ReqLLM.Context`, `ContentPart.image/2`, error mapping, `usage_callback`.
- `lib/leitor/dictionary.ex`: system/user context, "content, never instructions", and `normalize/1` with `clip/2`.
- `lib/leitor/ai/usage.ex`: usage validation and cost estimate.
- `test/support/language_stub.ex` plus `Application.put_env(:leitor, :language_adapter, ...)`: the stub approach.

**Prerequisite:** #48 (`fix/collection-ownership`) is merged. `update_collection/3` and `delete_collection/2` return `{:error, :not_found}` after a database ownership check. Do not start Task 3 before that.

## Global Constraints

Everything from phase 2 still applies:
- Conventional Commits PRs, squash-merged with `gh pr merge --squash --admin --delete-branch` after `Conventions` and `Elixir checks` pass.
- `mise run precommit` before every commit.
- The 7-day rule for new dependencies.
- `use Acervo.Schema` (UUID v7), and `%Scope{}` first on every context function.
- Minimal UI copy with icons, tooltips and DOM ids. English msgids, with pt_BR filled in.
- `Req.Test` stubs and no network in tests.
- CHANGELOG `[Unreleased]`, and new env vars in `mise.local.toml.example`.
- Chrome checks for UI work.
- The dev server runs on `:4200`; Postgres runs in the `acervo-db` container.

AI-specific rules for every task:
- **Captured content is untrusted.** Title, description, site, article text, image pixels and even the example link titles of collections come from the web. They enter the prompt only as one JSON-encoded data block inside a per-call random delimiter (see Task 4). The system prompt says that block is data, never instructions.
- **Output is validated, never trusted.** It must match the schema. Lengths are clamped, NUL and control characters are stripped, and the language must match a pattern. An existing collection is accepted only when its slug maps to one of the scope's collections loaded for this call. Acceptance re-checks ownership in the database.
- **No content or secrets in logs.** Log only link ids, model, token counts, cost, duration, and error class or HTTP status. Never log titles, URLs, prompts, responses or option lists that carry the API key. Keep ReqLLM telemetry payloads at the default (metadata only); never set `payloads: :raw`.
- **Strip NUL bytes** (`<<0>>`) from everything saved, as #42 asks. Postgres `text` rejects them anyway.
- **No network in tests.** Use `Acervo.FakeAIClient` (selected by `config :acervo, :ai_client`) everywhere except the adapter's own tests. Those run real ReqLLM code against `Req.Test` with `req_http_options: [plug: {Req.Test, Acervo.AI.Claude}]`.
- **Model calls cost money.** The only real calls happen in Task 1's single spike and in Task 7's verification. Never put a real call in a loop or a test.

#### Spike findings (2026-10-18)

The real call did not run: `ANTHROPIC_API_KEY` is empty in acervo's `mise.local.toml`. The attempt went through `Acervo.AI.generate_object/4` and is recorded in dev `ai_calls` as `error: "unavailable"`, with no HTTP request. Everything below comes from ReqLLM 1.28.0's source and from offline runs that sent the same request to a `Req.Test` plug.

- **Versions:** `req_llm` 1.28.0. Two transitive packages are locked below their newest releases for the 7-day rule: `llm_db` 2026.10.2 instead of .5, and `jsv` 0.26.0 instead of 0.26.1. LLMDB 2026.10.2 catalogues `claude-haiku-5-5` with adaptive thinking.
- **Option names:** `reasoning_effort`, `req_http_options`, `receive_timeout` and `max_tokens` are confirmed. `anthropic_structured_output_mode` is honored for objects **only inside `provider_options:`**; at the top level it is ignored.
- **Retries:** ReqLLM attaches its own retry step, which replaces Req's `retry:`. It retries 429, 529 and transient transport errors up to 3 times. `max_retries: 0` is what keeps one request per call.
- **Structured mode:** `:auto` picks JSON-schema mode. It sends the deprecated top-level `output_format` with the `structured-outputs-2025-11-13` beta, next to `output_config.effort` and adaptive thinking. `:tool_strict` sends a forced strict `structured_output` tool, and ReqLLM drops thinking and effort for it. The client keeps `:auto`; whether Anthropic accepts `output_format` is still unverified. If the real call returns 400, pass `provider_options: [anthropic_structured_output_mode: :tool_strict]`.
- **`total_cost`:** nil (`pricing: %{status: :unknown}`). ReqLLM prices Anthropic calls only when given a pricing context with `"inference_geo"`, and it never derives one. Per decision 7, `Acervo.AI.Rates` ports leitor's dated rate table, so every `ai_calls` row has an estimated cost: Haiku 5.5 at $0.10 per million input tokens and $0.50 per million output tokens, five times that above 100k prompt tokens. The fixture call (412 in, 57 out) estimates $0.0000697.
- **Headers on errors:** ReqLLM drops response headers on non-2xx object responses, so a 429 arrives as `{:rate_limited, nil}`. Task 5's backoff cannot rely on `retry-after`.
- **Validation:** ReqLLM's default `output_validation` does not check the object against the schema. The client validates it with `ReqLLM.Schema.validate/2` (JSV), and a mismatch is `:invalid_response`.
- **`Req.Test`:** `req_http_options: [plug: ...]` intercepts ReqLLM's transport, so the adapter tests run real ReqLLM code.

### Task 3: Suggestion triage in `Collections` and the image description in `Library`  *(Opus)*

**Files:**

- Test: `test/acervo/collections/suggestions_test.exs`, `test/acervo/library_test.exs`, `test/support/fixtures/collections_fixtures.ex` (add `suggestion_fixture/3`)

**Interfaces** (scope first; every write re-checks ownership in the database, using the `owned/2` and `authorize/3` pattern from #48):
- `@spec list_for_enrichment(Scope.t()) :: [%{slug: String.t(), name: String.t(), description: String.t() | nil, examples: [String.t()]}]`
  - At most 50 collections, ordered like `list_collections/1`.
  - `examples` holds the titles of the 3 most recent links in each collection, each clipped to 120 characters. Use one query with `row_number() OVER (PARTITION BY collection_id ...)`.
- `@spec replace_suggestions(Scope.t(), Link.t(), [%{optional(:collection_id) => Ecto.UUID.t(), optional(:proposed_name) => String.t(), reason: String.t()}]) :: {:ok, [Suggestion.t()]} | {:error, :not_found}`
  - It runs in one transaction.
  - It checks that the link is owned, deletes the link's *pending* suggestions, and inserts the new ones.
  - It drops:
    - a `collection_id` that is not the user's (database check);
    - a collection the link already belongs to;
    - a target (`collection_id` or `normalized_name`) the owner dismissed before for this link;
    - duplicates.
  - A `proposed_name` whose slug matches an existing collection of the user (`find_by_name_or_slug/2`) becomes that `collection_id`.
  - It keeps at most 3 and broadcasts nothing; the worker broadcasts.
- `@spec accept_suggestion(Scope.t(), Ecto.UUID.t()) :: {:ok, Collection.t()} | {:error, :not_found | Ecto.Changeset.t()}`. One transaction:
  1. Lock the row: `SELECT ... FOR UPDATE WHERE id = ^id AND user_id = ^user.id AND status = 'pending'`. If nothing comes back, return `{:error, :not_found}`.
  2. **With a `collection_id`:** confirm the collection is the user's (database check).
  3. **With a `proposed_name`:** reuse the user's collection with that name or slug, or create one with `Collection.changeset/2`. A lost race on the unique `(user_id, slug)` index re-reads by slug instead of failing.
  4. **Repoint:** among the user's other *pending* suggestions with the same `normalized_name` and no `collection_id`, first delete those whose link already has a pending suggestion for that collection, or already belongs to it. Then set `collection_id` on the rest.
  5. Insert the `collection_links` row with `source: :suggestion`, `on_conflict: :nothing`, and mark this suggestion `:accepted`.
  6. **After commit:** broadcast `{:collections_changed}` when a collection was created, and `Library.broadcast_updated/2` for this link and for every repointed link.
- `@spec dismiss_suggestion(Scope.t(), Ecto.UUID.t()) :: :ok | {:error, :not_found}` marks it `:dismissed` and broadcasts the link.
- `@spec accept_all_suggestions(Scope.t(), Link.t()) :: {:ok, Link.t()} | {:error, :not_found}` accepts every pending suggestion of the link, oldest first, then calls `finish_triage/2`.
- `@spec finish_triage(Scope.t(), Link.t()) :: {:ok, Link.t()} | {:error, :not_found}` dismisses the link's remaining pending suggestions, then calls `Library.mark_triaged/2`. ✓ means the owner has decided (see Open questions).
- **`Library`:**
  - `@spec update_image_description(Scope.t(), Link.t(), map()) :: {:ok, Link.t()} | {:error, :not_found | Ecto.Changeset.t()}` uses `owned/2`, `Link.image_description_changeset/2` and `updated/2`. Leave a `# phase 4: enqueue EmbedLink` comment.
  - `@spec change_image_description(Link.t(), map()) :: Ecto.Changeset.t()`.

- [ ] **Step 1:** Branch `feat/suggestion-triage`. Write the failing tests:
  - Accepting an existing-collection suggestion adds the link with `source: :suggestion` and marks it accepted. Accepting it twice gives `{:error, :not_found}`.
  - Accepting a new-name suggestion:
    - creates the collection;
    - reuses an existing one when the name differs only by case or accents (`"Inspiração"` and `"inspiracao"`);
    - repoints another link's pending suggestion with the same normalized name;
    - deletes the repointed duplicate when that link already had a pending suggestion for the collection.
  - **Isolation:**
    - user B accepting or dismissing user A's suggestion gives `{:error, :not_found}`;

1. **Release number vs spec.** The spec's Phases table says phase 3 ships as `0.4.0`, but main is already at `0.7.0`. This plan ships `0.8.0`, and the spec table should be updated in Task 7's PR.
2. **Slug vs id in the model contract.** The spec says suggestions are `{collection_slug | new_name, reason}`; the brief says "an existing collection id". The plan sends slugs to the model and stores ids. Slugs are shorter, readable, and not guessable across users. An unknown slug is dropped, so a hallucinated or injected id can never reach the database. Confirm.
3. **Collections input.** The spec sends up to 50 collections with their description and three example titles; the brief says names only. The plan follows the spec, because better suggestions are worth the few hundred extra tokens, and it treats example titles as untrusted. Confirm the cap of 50.
4. **"Accept all" scope.** The spec says it "accepts every pending suggestion of the selected links", but the UI has no multi-select. The plan does it per link (accept, then finish). Is an inbox-wide "accept all" in the column header wanted? It is riskier with untrusted suggestions.
5. **✓ dismisses the remaining suggestions.** The plan treats ✓ as "decided", so leftovers become `dismissed` and are never re-suggested for that link. The alternative keeps them pending and visible in the link column after triage. Owner's call.
6. **Enriching triaged links.** `backfill_enrichment/0` enriches every ready link, so already-triaged links get image descriptions, which phase 4 search needs, and dashed suggestions in their link column. Should the backfill skip suggestions for triaged links, enriching only the description and language?
7. **Cost source.** The plan stores ReqLLM's `usage.total_cost` from LLMDB pricing. If Task 1's spike shows it is nil for `claude-haiku-5-5`, should we port leitor's dated rate table (`Leitor.AI.Usage.estimate/2`) or accept token-only records? The plan defaults to tokens only and a nil cost.
8. **ReqLLM's structured-output parameter.** ReqLLM 1.27 sends Anthropic's deprecated `output_format`; current API docs use `output_config.format`. The Task 1 spike decides between the default mode and `anthropic_structured_output_mode: :tool_strict`. If both fail, upgrade ReqLLM or fall back to strict tool use.
9. **New collection names' language.** The plan tells the model to follow the language and style of the existing collections, else the page's language. Should it default to pt_BR instead, the interface default?
10. **Re-enrichment on capture retries and recaptures.** The plan skips enqueueing when `enriched_at` is set, except after a screenshot. If the owner wants a "re-run suggestions" action later, it becomes a small follow-up issue.

## Decisions (controller, 2026-10-18)

Answers to the open questions above; they override the plan text where they differ.

1. Ship as `0.8.0` and update the spec's Phases table in Task 7.
2. Slugs go to the model and ids are stored; unknown slugs are dropped.
3. Follow the spec: up to 50 collections with their description and three example titles, all treated as untrusted.
4. "Accept all" is per link only. There is no inbox-wide accept.
5. ✓ dismisses the remaining pending suggestions of that link.
6. The backfill enriches description and language for every ready link, but creates suggestions only for links still in the inbox (not triaged).
7. If ReqLLM's `usage.total_cost` is nil for the model, port leitor's dated rate table so every `ai_calls` row has an estimated cost.
8. Task 1's spike decides the structured-output mode, with strict tool use as the fallback.
9. New collection names follow the language of the user's existing collections; with none, the user's locale (pt_BR by default).
10. No re-run action now. A follow-up issue tracks it.
